# Upstream v1.1.65 integration (partial)

Seventh and final sequential checkpoint of the upstream v1.1.59–v1.1.65 batch
([#178](https://github.com/uv-genai/maya-tp/issues/178), epic
[#179](https://github.com/uv-genai/maya-tp/issues/179)). Upstream tag is
`c81fab6c`. It is recorded as merged at `d717bdf9`: the fork's tree plus 29
in-scope commits, with the AMD + NVIDIA pairing still excluded per the v1.1.62
decision. `7f1ba00d` keeps the TP2 first cause, and `736e1cd7` fixes the merged
test's includes. No production binary, launcher or config is changed.

## Scope

**Imported:**

- **#899.** GLM waits for the expert pool check's frees on Linux HIP before it
  sizes the pool (`MAYA_GLM_POOL_CHECK_WAIT_MS`). Its "no room" error names a
  smaller reserve only where that can make the room.
- **#860.** A GLM drafting step that stalls past `MAYA_GLM_STALL_S` (20 s)
  prints a `glm stall:` line saying where each GPU of the split is
  (`include/strata/platform/stall_watch.hpp`, with `stall_watch_test`).
- **#827.** An answer the engine stops itself on an error becomes the request's
  error on every API, not `length`. A non-streamed answer gets HTTP 422
  `engine_error` with the partial text. maya-ds4's END line carries the failed
  call and position.
- **Smaller changes:**
  - setup help and AMD-on-Ubuntu ROCm docs;
  - the CUDA compute-capability floor;
  - test isolation and skip fixes.

**Fork adaptations:**

- **END line.** maya-ds4 keeps "restart both ranks" as the recovery text when it
  drives a pair. The server parses the reason in either form.
- **TP2 pair-down.** The server's END handler keeps the TP2 pair-down beside the
  new reason capture. The pump now reads per process, so a restarted engine's
  lines never mix with the old one's.
- **First cause.** Upstream's engine-stopped path would have replaced a TP2
  pair's first cause (#88) with a generic "the engine stopped itself" error.
  `7f1ba00d` makes `_ended_itself` raise the retained first cause when the pair
  is down. It also adds three `serve.test_tp2_peer_loss` regressions.
- **Test include.** `736e1cd7` adds the `<vector>` include that the fork's copy
  of `glm_memory_test.cpp` needs for upstream's #899 checks. The first gates run
  failed to compile without it.

**Not imported:**

- the GLM link-helper and DeepSeek two-GPU helper commits, and the helper commit's own revert;
- the link-mode repeatable CPU-lane timing and their settings rows;
- `a35618f2`, a Windows NVIDIA pin guard on code the fork does not carry;
- `83cceadc` / `b4335ce6`, calibration on a busy GPU, built on the excluded mixed-GPU setup code;
- the expert-cache lend test tweak (that test left with vision lending).

`VERSION` stays `1.1.45`.

**Matched GLM repeat**

The checkpoint read lower than v1.1.64 on three GLM figures:

- the one-slot speculative short decode (38.97 → 35.51 tok/s);
- one two-slot mixed request;
- the GLM fanout (0.656 → 1.108 s).

v1.1.65 changes GLM decode code (the #860 stall watch), so a repeat alternated
the frozen v1.1.64 and v1.1.65 engines twice. It ran on the one-slot case and on
the two-slot case with three mixed waves and the injected peer loss
([glm-repeat](validation-v1.1.65/glm-repeat/)).

| Figure (3 runs per engine) | v1.1.64 | v1.1.65 |
| --- | --- | --- |
| Two-slot short / prefill spec decode, tok/s | 36.13 / 32.21 | 35.31 / 33.13 |
| Two-slot mixed aggregate (final wave), tok/s | 28.79, 30.30 | 29.58, 30.56 |
| GLM fanout, s | 0.656, 0.713, 0.983 | 1.108, 0.821, 1.086 |
| One-slot prefill / unicode / prefill-on decode, tok/s | 26.39 / 26.87 / 33.00 | 26.37 / 26.89 / 32.80 |
| One-slot **first** request (short-off), tok/s | 27.23 (27.17–27.30) | 26.86 (26.72–27.10) |
| One-slot **second** request (short-on, spec), tok/s | 37.21 (34.15–38.97) | 34.24 (31.89–35.51) |

Every completed request is identical across all runs and both engines. Only the
requests cut by the peer loss differ, in whether they had 0 or 1 token. Fanout
is the transport noticing the killed peer: the request after it fails in under
a millisecond in every run, and both engines span the same band.

**Remaining gap.** Two-slot figures and every later one-slot request match. The
two lower one-slot figures are the first two requests after load. The
harness's "cold prompt" there is the time spent waiting for the peer to finish
warming its expert tiers. The engine's own first prompt takes about 0.5 s in
both. That lag was 8–24 s in the v1.1.64 runs and 2–5 s in the v1.1.65 runs,
following the peer's page-cache read speed (1.0–3.7 GB/s). The second request's
speed falls as that lag shrinks, and the v1.1.64 run with the shortest lag also
read low (34.15). So the earliest requests seem to pay for warm-up still
settling, not for engine code. This is not proven. The only drafting-path cost
v1.1.65 adds is relaxed atomic stores and one 1 Hz watcher thread.
`MAYA_GLM_STALL_S=0` removes the watcher.
